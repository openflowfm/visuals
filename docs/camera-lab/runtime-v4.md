# Camera preview transport

Development-only authenticated routes; none is in the shipping binary.

- `GET /__bridge/camera/presets`: array of `{id,title,authors,thumbnail}`. Three camera presets (`camera:0`–`camera:2`) precede installed library rows. Catalog IDs are keys, never arbitrary paths. Thumbnail URLs are relative bridge routes and require the same token.
- `POST /__bridge/camera/settings`: required `speed` (0.1–3) and `persistence` (0–0.98); optional `presetId`, legacy numeric `preset`, and `resolution` (`360p`, `720p`, `1080p`). Missing resolution preserves the current size. Both renderer textures and output surface change; output headers remain authoritative. Failed shader translation returns 422.
- `POST /__bridge/camera/audio?rate=48000&gain=1`: exactly 512 or 1024 mono IEEE float32 little-endian samples, finite and within -1..1. Rate is 8000–192000 Hz, gain 0–4. Acknowledgement follows render-thread delivery. Clients keep one request in flight and send latest windows, not a backlog. PCM feeds the engine FFT; custom presets use bass, mid and treble. After 250 ms without fresh PCM the input is silence. `POST /__bridge/camera/audio/stop` clears input and audio state; camera stop also clears it. No device is opened or preference persisted by these routes.

1080p transfers 8,294,400 bytes per raw frame. It is an explicit quality choice, not a promise of 30 FPS on every machine. The browser controls microphone permission and input-device selection.

Camera output reuses one GPU texture, view and staging buffer at the current output size, with explicit unmapping after each read. Size changes replace this bounded allocation; camera stop releases it. Other application snapshots use their original path. The `X-Frame-Sequence` decimal unsigned integer increments after each native render refresh (including interpolation), never for a readback, and remains monotonic across preset/resolution/stop changes within one process. Consumers should count unique sequence values for frame rate, since repeated snapshots may contain the same rendered frame. A server restart resets the sequence. GPU readback is still synchronous; this change removes repeated allocation, not the GPU-to-browser transfer.

## Hardware encoded preview (macOS)

`GET /__bridge/camera/video?after=<sequence>` lazily starts a camera-only VideoToolbox hardware H.264 producer. Each response is an independent Annex B IDR frame with SPS/PPS (`Content-Type: video/h264`); it may skip intermediate frames. The actual codec string from the SPS is in `X-Video-Codec`. The client must capability-check that string and decode each response as a keyframe. Sequence, dimensions, and native snapshot timing use the same headers as raw output; `X-Frame-Timestamp` is presentation time in microseconds and `X-Encode-Ms` includes pixel upload through encode callback. Timestamp and sequence reset after a process restart.

A request returns only a sequence newer than `after`, waits at most 250 ms for one, then returns 204. Encoder failures return 503 and the client can use unchanged `/camera/output` raw transport. The producer targets 60 Hz, allows at most two pending encodes, and retains only the newest encoded frame. It reuses a persistent hardware session and pooled BGRA buffers, converting RGBA through Accelerate. Hardware acceleration is required, frame reordering disabled, and every encoded frame is validated as IDR. The bitrate target is 80 Mbps for recognizable fine contours.

Camera stop invalidates pending results and clears the latest output. A resolution change drains/releases the old session before creating another; callbacks from a stopped generation cannot republish frames. After two seconds without video requests, the producer releases its encoder and latest frame and waits without rendering. Allow that interval before comparing raw transport performance. No image, audio or encoded frame is persisted. This route and its framework bindings compile only with the dev bridge; ordinary OpenFlow rendering and capture are unchanged.
